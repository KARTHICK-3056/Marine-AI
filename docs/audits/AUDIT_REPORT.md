# Audit Report — 2026-08-04

**Repo context**
- **Project**: Marine AI — offline-capable YOLOv8 zooplankton detector for microscopy images
- **Stack**: Python 3.9+ (dev-tested on 3.13.7), Ultralytics YOLOv8 / PyTorch (CPU-only), OpenCV, Gradio 5.47 web UI, stdlib `unittest`
- **Purpose**: Upload a microscope image of a water sample; the app runs YOLOv8 inference, draws labeled bounding boxes for 13 zooplankton taxa, and renders a count/confidence summary — intended for offline field deployment on a Raspberry Pi 5
- **Constraints observed from the repo**: no CUDA GPU available at the target deployment (CPU-bound inference), must stay usable on low-bandwidth/offline field devices, no `.git` repository initialized yet (paths, LFS config, etc. are pre-init)

**Note on scope**: this repo already went through one audit → fix cycle (this file's prior contents, now superseded by this pass, and `FIX_REPORT.md`, which record 14 previously-fixed issues — hardcoded `D:\` model path, unpinned deps, `share=True` default, unescaped HTML, un-downscaled uploads, a TOCTOU port race, etc.). This pass re-verified all 14 of those fixes are actually present in the current code (confirmed by direct read of [app.py](app.py) and by re-running the test suite — see below) and did **not** re-list them as open issues. This pass instead audits the *current* state of the repo for anything the previous cycle missed or left behind, plus documentation that fell out of sync with the code changes.

### [ISSUE-001] README installation/usage instructions still hardcode a Windows `D:\Marine-AI` path, contradicting the app's own (already-fixed) relative path resolution
- **Severity**: High
- **Category**: Documentation & Developer Experience
- **File(s)**: `README.md` (lines 147, 153, 188, 200, 212, 221, 227, 252, 309, 324, 360, 363)
- **Description**: `app.py`'s `load_model()` was fixed in the prior audit cycle to resolve the model path relative to the script's own directory (`os.path.dirname(os.path.abspath(__file__))`), specifically so the app isn't tied to one machine's drive layout. `README.md` was not updated to match: it still tells users to `cd D:\Marine-AI`, confirms the model must sit at exactly `D:\Marine-AI\models\best.pt`, shows the Troubleshooting section's example error as `ERROR: Model file not found at D:\Marine-AI\models\best.pt`, and draws the Project Structure diagram rooted at `D:\Marine-AI\`. This is the exact class of bug ISSUE-001 fixed in code — reintroduced in docs. It's also self-contradictory: this project's stated primary deployment target is a Raspberry Pi 5 (Linux), which has no `D:\` drive at all, so a user following the README's own instructions on the project's own target hardware cannot succeed.
- **Evidence**:
  ```
  README.md:147   # Alternatively, download and extract to D:\Marine-AI
  README.md:153   cd D:\Marine-AI
  README.md:188   D:\Marine-AI\models\best.pt
  README.md:309   **Model File**: `D:\Marine-AI\models\best.pt`
  README.md:360   ERROR: Model file not found at D:\Marine-AI\models\best.pt
  ```
- **Suggested fix**: Replace all `D:\Marine-AI\...` references with a placeholder that matches the actual behavior — e.g. `<repo-root>/models/best.pt` or `./models/best.pt`, and add a short note that `MODEL_PATH` can override the location via environment variable (this override already exists in `app.py` but is undocumented in the main install/usage flow — it's only mentioned later in the Raspberry Pi tuning table).
- **Risk if unfixed**: New contributors and field-deployment operators (the Raspberry Pi audience this whole project is built for) hit a misleading setup path and either get confused or manually recreate the drive-letter coupling that was already fixed once.
- **Effort estimate**: Small
- **Dependencies**: None

### [ISSUE-005] No exception handling around the YOLO inference/annotation path — failures surface as raw, undiagnosable errors instead of the app's own friendly error pattern
- **Severity**: Medium
- **Category**: Error Handling & Resilience
- **File(s)**: `app.py:113-141` (`detect_zooplankton`)
- **Description**: `detect_zooplankton()` already has a graceful, styled error path for "model failed to load at startup" (lines 95-102). But nothing wraps the actual per-request work — `model.predict(...)` and the subsequent box/label-drawing loop — in `try`/`except`. Any runtime exception here (a corrupted/adversarial image PIL decodes but YOLO chokes on, a `DecompressionBombError` from PIL's built-in bomb protection on a pathological upload, an unexpected tensor shape from a future model swap via `MODEL_PATH`) propagates straight out of the Gradio event handler instead of degrading to the same kind of styled error card the "model not found" case gets. Gradio catches it at the framework level and shows a generic error toast to the user with no actionable message, and the only diagnostic trail is whatever prints to the server's stdout/stderr.
- **Evidence**:
  ```python
  results = model.predict(source=img, conf=0.3, imgsz=YOLO_IMGSZ, save=False, show=False, verbose=False)
  ...
  for box in results[0].boxes:
      ...  # no try/except anywhere in this block
  ```
- **Suggested fix**: Wrap the `model.predict(...)` call (and ideally the whole detection body from line 104 onward) in a `try/except Exception`, log the exception server-side, and return the same three-tuple shape (`input_image, input_image, error_html`) with a styled message consistent with the existing "Model Not Found" card, e.g. "Analysis failed — try a different image."
- **Risk if unfixed**: A single malformed upload produces an opaque failure for a non-technical field user (marine biologist, aquaculture technician) with no way to self-diagnose, and no server-side record beyond a raw traceback.
- **Effort estimate**: Small
- **Dependencies**: None

### [ISSUE-008] Importing `app.py` has heavy, non-obvious side effects: env var mutation, model loading, and full UI graph construction all run at import time
- **Severity**: Low
- **Category**: Architecture & Maintainability
- **File(s)**: `app.py:14-15, 30-32, 85, 208-261`
- **Description**: There's no guard separating "define things" from "do things" — setting `YOLO_AUTOINSTALL`/`GRADIO_ANALYTICS_ENABLED`, capping CPU thread pools, loading the ~50MB YOLO model (a multi-second operation that prints to stdout), and building the entire `gr.Blocks` UI graph all execute unconditionally as soon as `import app` runs, not just under `if __name__ == "__main__":`. This is why `tests/test_app.py` takes ~4 seconds to run a handful of unit tests, and why any tool that merely inspects the module (a linter plugin, a doc generator, a future CI static-analysis step) pays the full model-load cost and requires `models/best.pt` to be present just to import the file.
- **Evidence**: `model, MODEL_PATH = load_model()` at `app.py:85` runs at module scope; the `with gr.Blocks(...) as demo:` block at `app.py:208` is similarly top-level, not inside `if __name__ == "__main__":`.
- **Suggested fix**: This is explicitly the kind of change the already-deferred `ISSUE-010` (splitting `app.py` into modules) is well-suited to address — when that split happens, move model loading and UI construction behind functions called only from the `if __name__ == "__main__":` block or an explicit `create_app()`/`get_model()` entry point, and have tests call those explicitly rather than relying on import-time side effects.
- **Risk if unfixed**: Slower test/dev iteration loop; tighter coupling between "can I import this file" and "is the model file present," which will matter more once CI (ISSUE-004) is added.
- **Effort estimate**: Medium (best done together with the already-deferred module split)
- **Dependencies**: Related to the deferred `ISSUE-010` module-split noted in `FIX_REPORT.md`

### [ISSUE-009] Detection confidence threshold is hardcoded, unlike its sibling tunables
- **Severity**: Low
- **Category**: Architecture & Maintainability
- **File(s)**: `app.py:113`
- **Description**: `MAX_DIMENSION` and `YOLO_IMGSZ` are both read from environment variables with documented defaults (and the README's Raspberry Pi tuning table explicitly documents both as field-adjustable knobs). The detection confidence threshold passed to `model.predict(conf=0.3, ...)` is a bare literal, not following the same pattern, so a field operator who wants to trade off false positives vs. missed detections has no way to do so without editing source.
- **Evidence**: `results = model.predict(source=img, conf=0.3, imgsz=YOLO_IMGSZ, ...)` — `0.3` is a literal; `YOLO_IMGSZ` two tokens later is `os.environ.get(...)`-backed.
- **Suggested fix**: Extract to `CONFIDENCE_THRESHOLD = float(os.environ.get("CONFIDENCE_THRESHOLD", 0.3))` alongside the other tunables near the top of the file, and add it to the README's tuning table.
- **Risk if unfixed**: Minor inconsistency; not a functional bug, but a small ergonomics gap in an app whose whole design philosophy (per its own docs) is "tune via env var, no code edits needed in the field."
- **Effort estimate**: Trivial
- **Dependencies**: None

### [ISSUE-010] No EXIF orientation correction before processing/annotating uploaded images
- **Severity**: Low
- **Category**: Correctness & Logic Bugs (edge case)
- **File(s)**: `app.py:104`
- **Description**: `input_image.convert("RGB")` normalizes color mode but does not apply `PIL.ImageOps.exif_transpose()` first. Images carrying an EXIF orientation tag (common from phone/tablet cameras, less common from the project's primary USB-microscope target but still a plausible upload source, e.g. someone photographing a physical printout or a microscope's own screen) will be processed and annotated in their raw stored pixel orientation, so the displayed "before"/"after" images and bounding boxes could appear sideways or upside-down relative to how the image previews correctly in most viewers (which do respect EXIF orientation).
- **Evidence**: `img = np.array(input_image.convert("RGB"))` — no orientation normalization step.
- **Suggested fix**: `input_image = ImageOps.exif_transpose(input_image)` before `.convert("RGB")`, using PIL's own `ImageOps` module (no new dependency).
- **Risk if unfixed**: Low-likelihood given the primary USB-microscope input source, but produces a confusing (sideways) result with zero error signal if it ever occurs.
- **Effort estimate**: Trivial
- **Dependencies**: None

## Cross-Cutting Observations

1. **Documentation lags code by a full fix cycle.** Every High/Medium documentation issue in this pass (ISSUE-001, 002, 011) is a documentation-vs-code mismatch, not a code defect — the prior audit cycle correctly fixed real bugs in `app.py` but didn't sweep `README.md` for matching updates. Future fix passes should treat "update the docs describing the changed behavior" as part of the same unit of work as the code fix, not a follow-up.

3. **Testing has grown organically alongside fixes** (12 tests, all tied to specific prior ISSUE numbers) rather than from systematic coverage planning — which is exactly why the two branch-coverage gaps in ISSUE-006 exist. Worth a coverage pass once ISSUE-004 (CI) and ISSUE-010 (module split, deferred) land.
